# Configuración Supabase — solo entorno autorizado

Fuente de verdad de FC-07 en el Desktop (solo **lectura**, no modificar): `supabase/migrations/20261014000100_prepare_two_branches.sql`; estado de implementación en `docs/architecture/SUPABASE.md` y pruebas de migración aislada en `tests/FC07/README.md`. **El archivo de migración no acredita que esté desplegado en Impulso Digital.** No ejecutar `supabase link`, `db push`, SQL ni crear usuarios desde esta web.

1. El responsable del proyecto verifica el destino, RLS y grants efectivos y valida FC-07 en una instancia descartable antes de decidir un despliegue separado. No conectar esta app a producción sin autorización.
2. En un proyecto **de prueba** con FC-07 aplicada y políticas/grants auditados, un administrador autorizado crea usuarios en Supabase Auth, sucursales en `public.branches` y asignaciones en `public.branch_users` mediante un procedimiento seguro **fuera del navegador**. No se asignan sucursales automáticamente ni se usan usuarios locales Desktop como identidades Auth.
3. Copiar `.env.example` a `.env.local`. Usar `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` (clave pública publishable/anon admitida por el proyecto). `VITE_*` queda embebido en JavaScript: jamás incluir `service_role`, `SecretKey`, contraseña o clave privada. `.env.local` está ignorado por Git. No reutilizar la configuración antigua `Supabase__SecretKey` del Host Web.
4. En Auth, aprobar el método email/contraseña, acceso a la aplicación y origen autorizado; registrar las URL de redirección permitidas según el proyecto. Este frontend no implementa alta/recuperación de contraseñas. Probar JWT reales, RLS y grants remotamente antes de distribuir.

Consultas hechas por el cliente autenticado: `branch_users` (`branch_id`, por `user_id=auth.uid()`); `branches` (`id,name,time_zone`, solo ids asignados); `branch_audit_events` (`branch_id,event_code,outcome,occurred_at,contract_version`, filtros/paginación server-side). En la migración FC-07 `anon` carece de acceso y `authenticated` tiene únicamente SELECT por columna; RLS compara con `branch_users`. No se lee `branch_installations`, `ingestion_receipts`, identificadores de operación, `audit_logs` locales ni tablas de personas. Si no hay asignación, se deniega la vista; si un grant/RLS falla, se muestra error o acceso denegado, **no** se desactiva RLS.

El selector del navegador no es una frontera de seguridad: el servidor/PostgREST **debe** imponer RLS. La prueba SQL de FC-07 usa `SET ROLE` con claims simulados; no prueba JWT reales ni proyecto remoto. Revisar revocación de asignaciones con sesión abierta, permisos efectivos de PostgREST, cache y exposición de columnas. El estado de roles del Desktop no se reutiliza.

**Rama integración no desplegada:** el endpoint `branch-bridge` y la migración adicional viven en el repositorio Desktop. `VITE_BRANCH_BRIDGE_ENABLED` es `false` por defecto; cambiarlo solo tras autorización y verificación remota del endpoint. La web consulta `installations`/`status` y envía `refresh` usando el JWT del usuario; no lleva clave privilegiada. El backend comprueba `branch_users`, `branch_refresh_grants`, instalación activa, agente activo y `branch_cloud_activation` (apagado por defecto); limita simultaneidad y frecuencia. El Desktop continúa cerrado sin productor de catálogo aprobado. Instrucciones detalladas en `docs/operations/INTEGRACION-CLOUD.md` del Desktop. No se exhiben agregados sin catálogo aprobado.

**Permisos adicionales por rol:** FC-07 solo representa asignación `(branch_id,user_id)`; no tiene roles ni acciones diferenciadas. Para agregarlos se requiere definir política de roles con producto/seguridad, migración separada con tabla/claims verificables por servidor, nuevas RLS y grants por operación, tests A/B/roles con JWT reales y aprobación de despliegue. No habilitar escritura ni inferir rol por email o metadatos editables del usuario.
